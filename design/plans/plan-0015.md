현재 상태 (확인 완료):
- `repository._SELECT_POSTINGS`는 모듈 상수. `postings p`에 `bookmarks b`·`hides h`를 `deleted_at IS NULL` 조건으로 LEFT JOIN. `_row`가 `bookmarked`·`hidden`을 bool로 바꾸고 목록은 `description`을 pop. `list_postings(company, min_level, include_deleted=False, include_hidden=True, interests_only=False, since=None)`, `get_posting(id)`는 `p.deleted_at IS NULL`. `delete_postings`는 `("bookmarks", "hides", "feedbacks")` 순으로 지운 뒤 postings 삭제

- `Repository(readonly=True)`는 스키마·`_migrate`를 건너뛴다. `feedback_for`가 `sqlite_master`로 테이블 유무를 확인하는 선례. `test_cli.old_db_0013`과 `test_repository.old_db_0013`(별도 헬퍼, `re.subn`으로 `n == 1` 확인)이 각각 0.4.0 스키마 DB를 만든다 (`SCHEMA` 문자열에서 컬럼·테이블을 제거하는 방식이라 두 곳 모두 `applications` CREATE도 제거해야 한다. 안 하면 "옛 DB"에 `applications`가 생겨 readonly 폴백 테스트가 헛돈다)
- `POST /postings/{id}/feedback`도 `found()` → `get_posting`을 거치므로 삭제 조건 변경이 그대로 전파된다
- `api.py`: `bookmark(id, on)` 헬퍼 + PUT/DELETE 두 라우트, 반환 `{posting_id, bookmarked}`. `GET /postings`는 `list_postings(company, min_level)` 기본값. `found(id)`가 `get_posting` 404
- `jobs._run_company`: `delete_postings(company, exclude ids)` 한 줄. 테이블 목록은 repository 쪽
- CLI: `POSTING_FIELDS`·`FULL_FIELDS`·`DETAIL_FIELDS` 튜플, `_postings`는 `include_hidden=False, interests_only=True`, `_posting`은 `get_posting` 없으면 `not_found`. `test_cli.py`의 `POSTING_KEYS`·`FULL_KEYS`·`DETAIL_KEYS`가 키 집합 고정, `test_posting_legacy_db`가 0.4.0 DB로 `posting`·`postings --full`
- SKILL.md 34행 "`not_found` (exit 1): `posting <id>`의 공고가 없거나 삭제됨", 명령 핀 `gethired~=0.5.0`
- 프론트: `Tab = "postings" | "bookmarks" | "hidden" | "companies"`, `TAB_LABEL`·`TAB_PATH`·`TABS`. `toggleFlag(p, flag)`는 boolean 플래그 전용(`FLAG_API`), `pending` ref로 중복 방지, 성공 `true`. `shown = postings.filter(관심회사)`, `count.bookmarks/hidden`은 `shown` 기준. `PostingsTab`은 `!p.hidden` 필터, `BookmarksTab`은 `bookmarked && !hidden`, `HiddenTab`은 `hidden`. 탭·카드는 `onToggleBookmark`·`onToggleHidden`만 받는다. `PostingDetail`은 원본 `postings`에서 id로 찾고 없으면 자기 복사본, `toggle(flag, fn)`이 `!listed`면 복사본 갱신. `PostingCard`가 `Deadline`·`StarButton`·`HideButton` export(상세 재사용), `.star`·`.hide` 스타일 공유. 픽스처 `makePosting`·`makeDetail`

def get_posting(self, posting_id)                              # 같은 삭제 조건. 응답에 deleted_at 포함(p.*)

    # 활성 공고(deleted_at IS NULL) 없으면 None(→ 404). 이미 지원완료면 created_at 유지(멱등, bookmarks와 같은 ON CONFLICT WHERE)
    # 해제 후 재지원은 created_at·updated_at = now, stage NULL. 반환 {"applied_at", "stage"}
def clear_application(self, posting_id: int, now: str) -> bool

```
PUT    /api/postings/{id}/application   200 {posting_id, application: {applied_at, stage: null}}
                                        404 없음·마감(deleted_at)
DELETE /api/postings/{id}/application   200 {posting_id, application: null}  (마감이어도)
                                        404 공고 행 없음
GET    /api/postings · /api/postings/{id}   기존 + application: {applied_at, stage} | null, deleted_at: str | null
                                        목록은 마감된 지원완료 공고를 포함한다. 그 외 마감 공고는 기존대로 제외
```

### CLI (B가 구현·문서화)
```
gethired postings        지원완료 제외(include_applied=False). 키 변화 없음
gethired posting <id>    DETAIL + application: {applied_at, stage} | null. 마감된 지원완료 공고도 반환
                         not_found = 없음, 또는 지원완료가 아닌 삭제 공고
```

## 수동 검증 (사용자)
저장소 dev DB(`backend/data/app.db`)로 충분하다. 스크래핑·LLM 불필요.
1. 공고 탭 카드의 체크 → 즉시 사라지고 지원완료 탭 배지 +1, 탭에 지원일과 함께 보임. 새로고침 후에도 유지
2. 북마크 공고·숨긴 공고 각각 지원완료 → 해당 탭에서 빠짐. 지원완료 탭에서 해제 → 각각 북마크 탭·숨김 탭으로 복귀, 공고 탭엔 안 보임
3. 상세에서 체크 → 머문 채 활성, 뒤로가기 → 목록에 없음
4. 두 건 연속 지원 → 최근 것이 위
5. 회사 탭에서 지원한 회사의 관심 해제 → 지원완료 탭·배지에 남음. 다시 관심 등록
6. 마감 재현: `sqlite3 backend/data/app.db "update postings set deleted_at='2026-10-26T00:00:00+00:00' where id=<지원한 id>"` → 새로고침 → 지원완료 탭에 "마감" 배지로 남고 상세 열림. 카드·상세의 별·숨김이 disabled. 해제 → confirm → 취소면 유지, 확인이면 사라짐. 다른 마감 공고(비지원)는 안 보이는지. 끝나면 `deleted_at=NULL`로 되돌리고, 확인까지 했다면 공고 탭에서 다시 지원완료
7. `uv run gethired posting <지원한 id> --json`에 `application`, `postings --json`에서 빠짐. 6번 상태에서 `posting`은 반환되고 비지원 마감 id는 `not_found`
8. 결과(이상 동작·어긋난 계약)를 루트 `handoff.md`에 남긴다
