## 수동 검증 (사용자, provider 로그인 상태)
저장소 밖 임시 디렉토리로 DB·이력서를 분리해 실제 데이터를 건드리지 않는다. 공고는 `backend/out/{toss,daangn}.json`(이미 수집됨. 3단계 후 `just scrape toss daangn`으로 갱신)을 쓴다. 주의: justfile이 `export DB_PATH :=`·`export RESUME_DIR :=`로 환경변수를 덮어쓰므로 셸 env가 아니라 `just` 변수 오버라이드로 넘긴다.

1. 합성 이력서 3종을 `$TMPDIR/roles-check/{fe,ios,ml}/resume.md`에 만든다. 각 200~300자: 직군·연차·핵심 기술 3~5개·프로젝트 2개·도메인 1개. 예: fe = React·TypeScript·Next.js 4년, 커머스 웹 / ios = Swift·SwiftUI·Combine 5년, 핀테크 앱 / ml = PyTorch·추천 모델·서빙 3년, 광고
2. 각각 `just DB_PATH=$TMPDIR/roles-check/<r>/app.db RESUME_DIR=$TMPDIR/roles-check/<r> match toss daangn --planted --out $TMPDIR/roles-check/<r>/matches.json` 를 돌리고, 바로 `cp backend/out/fit.md $TMPDIR/roles-check/<r>/fit.md` (fit.md는 실행마다 덮어써진다)
   - `--limit`은 쓰지 않는다. `load_postings`가 회사 알파벳순으로 합친 뒤 앞에서 자르므로 당근 33건이 먼저 오고 토스 App이 빠질 수 있다. 토스 약 150건 + 당근 33건 × 3종 ≈ 550건 판정, 약 $6. 줄이려면 회사별로 따로 돌린다
   - `--planted`는 iOS·영업 공고가 포함된 고정 세트라 ios·fe 검증에 그대로 쓴다
3. 각 디렉토리의 `fit.md`와 `matches.json`에서 확인
   - fe: Frontend 공고 exclude 0건. Backend 공고는 exclude 또는 stretch. 디자인·PO 공고(있다면) exclude. `planted-unfit-ios` exclude
   - ios: App(iOS) 공고 stretch 이상, Android는 stretch 이상(인접), Backend는 대부분 exclude. `planted-unfit-ios` strong
   - ml: ML 공고 exclude 0건, Data Engineering은 stretch 이상
   - 공통: `planted-unfit-sales` exclude
4. `roles` 빈 프로필 경로 (규칙 2의 "비어 있으면 skills·domains로 추정" 분기): fe의 캐시를 비워서 한 번 더 돌린다. `get_profile`은 키가 없을 때만 재추출하므로 빈 리스트는 캐시가 그대로 쓰인다
   ```
   sqlite3 $TMPDIR/roles-check/fe/app.db "update profile_cache set profile = json_set(profile, '$.roles', json('[]'))"
   just DB_PATH=... RESUME_DIR=... match toss daangn --planted --out $TMPDIR/roles-check/fe/matches-noroles.json
   ```
   Frontend 공고 exclude 0건이 유지되면 통과. 크게 달라지면 프롬프트의 추정 규칙 문구를 보강
5. 회귀: 실제 이력서로 같은 명령을 `--planted`와 함께 돌려 strong·good 건수를 이전 `backend/out/fit.md`와 비교. `planted-fit` strong, `planted-unfit-ios`·`planted-unfit-sales` exclude여야 한다. 차이가 크면(±30% 이상) 프롬프트의 소프트 불일치 문구를 재조정
6. 결과 요약(직군별 등급 분포 표, 빈 roles 비교)을 handoff.md에 남긴다
