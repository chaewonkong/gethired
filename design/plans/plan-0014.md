### API (A가 구현, C가 사용)
```
GET  /api/postings            기존 + breakdown (legacy면 null). description은 포함하지 않는다
GET  /api/postings/{id}       200: Posting 필드 + description: str | null, requirements: str[] | null, preferred: str[] | null,
                                   breakdown: {skills, domain, seniority, preferred} | null,
                                   feedback: {items: str[], created_at, current: bool} | null
                              404: 없음 또는 deleted_at (detail "posting not found")
POST /api/postings/{id}/feedback
                              200: {posting_id, feedback: {items, created_at, current: true}}  (캐시 적중이면 LLM 미호출)
                              404 공고 없음·삭제 / 409 {code: "job_running", message} (jobs.is_locked(), 시작 시점 1회만)
                              401 {code: "login_required", provider, message, login_command} (scrape와 같은 형태)
                              400 {code: "no_resume", message} (profile_loader가 FileNotFoundError)
                              502 {code: "llm_error", message}
```
순서: 404 → 409 → 캐시(`profile_hash()`) → 로그인 선체크 → `profile_loader` → 생성 → 저장. legacy 공고(description·requirements null)도 허용. 생성 도중 스크래핑 시작·provider 변경은 막지 않는다.

### CLI (B가 구현, D가 문서화)
```
gethired posting <id> [--json] [--body]
  → {id, company, title, fit_level, score, fit_reason, apply_url, deadline, scraped_at,
     summary, gaps, tech_stack, requirements, preferred, breakdown, feedback}
    --body면 description 추가 (기본 제외: 스킬이 에이전트 컨텍스트로 들어가는 경로)
    feedback = {items, created_at, current} | null (캐시만. 생성하지 않는다). legacy 컬럼은 null
  오류 code: not_found (exit 1) 없음·삭제. not_onboarded 기존
gethired postings --full  → 기존 FULL 키 + breakdown
```

### 프론트 오류 클래스 (C 내부, 계약 고정)
`api.ts`: `NotFoundError`(404) 신규, 401은 기존 `LoginRequiredError`, 409는 기존 `JobRunningError`, 502·400은 `LlmError(message)` 신규(400 `no_resume`는 온보딩 전엔 상세에 못 들어가므로 같은 토스트로 처리).

## 수동 검증 (사용자, provider 로그인 상태)
저장소 밖 임시 DB로 분리한다. justfile이 `DB_PATH`·`RESUME_DIR`를 export하므로 `just DB_PATH=... RESUME_DIR=...` 오버라이드로 넘긴다.
1. 기존 dev DB를 복사해 `$TMPDIR/detail-check/app.db`로 두고 `just DB_PATH=... scrape toss daangn`. 저장 공고 전체가 재판정 대상이고 본문 한도 6000·배치 10이라 비용 약 $8~10(토스 150 + 당근 30). 끝나면
   ```
   sqlite3 ... "select count(*) from postings where company in ('toss','daangn') and breakdown is null and deleted_at is null"   -- 0
   sqlite3 ... "select count(*) from postings where company in ('toss','daangn') and description is null and deleted_at is null" -- 0
   ```
   (`has_description=False`인 소스(현대차)는 description null이 정상이라 회사 조건을 붙인다)
   job 결과의 `excluded`가 0이 아니면 그 수만큼 행이 줄었는지(`count(*)` 전후 비교) 확인
